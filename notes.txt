Problems we are trying to solve and some other things to keep in mind:
- Nodes can die
- Nodes can come back around
- Nodes can miss a message
- Messages could be reordered
- There can be a delay in the network and a message might reach a particular node a bit later than the others.
- There can be multiple clients.
- Multiple clients may issue concurrent requests.
- If a node comes back to life then it must be made up to date with the other nodes.
- At any point, the nodes may have different uncommitted suffixes, but the committed part of the log must be consistent, and once an entry is committed it will not disappear.
- So the committed history must be consistent.
- If a node dies, it can no longer transfer any of its data through the network anymore.
- There is no central observer, so you can't execute commands like: " Go to each node and check which one is the most up to date." Also even if a node is alive, it may so be that at an instance of time, it is able to be reached by live nodes x and y but not by the live node z. So this node according to z will be considered dead. So making a particular node the central observer is also not an option.
